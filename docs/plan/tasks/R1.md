# 任务 R1：建立平台格式与验证环境基线

> 本文只维护该任务的实施与验收详情。状态、优先级、依赖、执行顺序和阻塞以 [Dashboard](../Dashboard.md) 为唯一权威来源。

## 背景与目标

为每个平台建立带来源、日期、目标版本和证据等级的格式基线，给后续 Packager 与 Executor 提供可验证输入。

## 执行上下文

公共能力和授权要求见 [CONTRACTS §3–4](../../CONTRACTS.md#3-执行请求结果和能力)。

- **权威需求**：[设计文档](../../../../dev-harness-runtime-design.md) §14、§19–21、§29、§33、§49；[资料评估](../Readiness.md)。
- **代码入口**：从下列影响文件进入。初始化时目标项目为空，所列实现与测试路径均为建议新建路径，不能当作已有代码。
- **相关测试**：打开官方规范并记录稳定版本或校验摘要；离线校验最小 manifest 样例；只读盘点宿主版本和测试条件。
- **必须保持的不变量**：插件格式与执行能力分别取证；缺少独立 Session 证据时 freshSession 不能为 true。
- 已有官网初查见 [资料评估](../Readiness.md)；DSH 目标按设计 §19.2 为 `0.1.5-rc.1`，[旧 rc.8 集成基线](../../../../dev-harness-dsh/docs/integration/DSH_API_BASELINE.md) 仅作历史对照。

## 范围

- **包含**：五个平台及 Portable Agent Plugin 的官方格式、必需字段、入口、能力探测方式；宿主、操作系统和 smoke 条件清单。
- **不包含**：把官网说明当作运行成功；隐式启用模型调用、安装用户级插件或发布产物。

## 建议实施顺序

1. 重读 Dashboard 与本任务，检查来源是否漂移；从资料评估对应条目和已形成的决策记录确认输入。
2. 先建立本任务验收所列的正常、异常和边界样例，再在范围内实现或完成决策取证；不为迁就实现修改公共协议。
3. 按下列验收逐项验证，记录真实命令、环境、结果和稳定证据；更新相关事实文档，再按 Planning 生命周期收口。

## 验收标准

- [ ] 六类产物均有规范出处、最小 fixture、必需字段清单；无法获取的规范有明确缺项。
- [ ] 记录 Codex / DSH 可用测试入口；区分文档支持、离线验证、真实宿主运行三种证据。
- [ ] 固定 DSH `0.1.5-rc.1` 的公开 API / Bundle 规范、实际组件依赖和版本输出证据；记录相对 rc.8 的兼容差异，不把宿主版本机械套用到所有组件包。
- [ ] Windows / Linux / WSL 的可执行测试环境与无法运行的项目均被记录。
- [ ] 任何尚无规范或运行证据的能力在后续任务中保持门禁，不因 R1 文档完成自动启用。

- [ ] 自动执行前取得 authorizationEnforced 证据；Worker、Core 验证进程与提交 hook 均受授权约束，不能只靠 prompt 禁令。

## 已确认决策

- 项目名 `dev-harness-runtime`，CLI 全部使用 `dhr`。
- DSH 目标宿主固定为 `0.1.5-rc.1`；不直接继承 rc.8 的兼容性结论。
- 状态根目录统一为 `$(git rev-parse --git-path dev-harness-runtime)/runs/`；具体布局以设计 §10 为准。
- 插件格式与执行能力分别取证；缺少独立 Session 证据时 freshSession 不能为 true。

## 未知项与停止条件

- **已知风险**：来源升级、接口不完整或环境不足可能使验收不可复现；不能将设计示例或历史通过记录当作本次运行证据。
- **未决问题**：DSH `0.1.5-rc.1` 的 API 与组件兼容性；Antigravity Plugin 规范的有效来源、Codex manifest 的精确格式、其他宿主目标版本与可用运行环境。
- **停止条件**：需要扩大范围、改变公共语义或验收、使用无证据宿主能力，或发现 Git / Planning 外部漂移时停止实现，回到 Dashboard 对齐。
