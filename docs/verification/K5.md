本机 Codex CLI 为 0.154.0。隔离的临时空工作区使用 `codex exec --ephemeral --ignore-user-config --sandbox read-only --skip-git-repo-check --json --output-schema <schema> -C <temp>` 运行合成提示，退出码 0，依序返回 `thread.started`、`turn.started`、`item.completed`、`turn.completed`。本次 thread ID 为 `01a0afef-b904-7f51-ae52-1c358829c000`，最终内容通过固定 JSON Schema，为 `{"status":"ok"}`。此前独立只读会话也曾取得真实 thread 事件；本次没有发送项目源码、运行 Planning Task 或修改仓库。

第二个合成只读会话返回不同 thread ID `01a0aff1-c85b-7e63-963a-06f6b0d87d8c`。该会话请求在临时目录创建测试文件，退出时文件不存在；仅凭文件未出现不能证明宿主对所有工具调用均强制拒写，更不能证明允许的 Task 路径可写而其余路径拒写。

另在一个只含空 `workspace/` 与同级 `outside/` 的临时目录调用 `codex exec --ephemeral --ignore-user-config --sandbox workspace-write --skip-git-repo-check --json -C <workspace>`，合成提示要求先写工作目录内 `inside.txt`，再尝试写工作目录外 `outside/outside.txt`。会话 ID 为 `01a0aff9-bfc8-7ab1-b312-280d1294c4b4`，退出码 0，事件含两次 `command_execution`；结束时两个文件都存在，临时目录随后删除。本机此模式允许写入工作目录外的临时路径，不能充当 Core 固定的逐 Task 写入白名单。该反例不推断其他主机或版本的行为。

这些事实只证明新会话事件与合成结构化输出入口可用，并提供 `workspace-write` 在本机不能约束同级临时路径的反例。尚未证明逐 Task 文件写入白名单、外部动作禁止、取消后整个 Worker 树静止、结果与 Core 请求身份绑定、完成结果及恢复使用不同 Session。不能凭 CLI help 或上述合成会话推定满足 `authorizationEnforced:true`。因此 `adapter-codex` 仍不注册 TaskExecutor；`dhr run --adapter codex` 继续明确拒绝，而不会退化为父会话手工执行。MVP 三 Task 自动验收尚未运行。

2026-09-18 在另一个空临时目录使用相同 `--sandbox read-only` 入口要求真实 shell 工具分别写入工作区内外的文件。thread `01a0b01b-d3c6-7e81-a486-660921994fcd` 的两次重定向均返回 read-only file system；独立 `find` 确认两个文件都不存在。又启动只绑定 `127.0.0.1:18765` 的临时 HTTP 服务，thread `01a0b01c-d01d-7221-8074-ad08cc30b627` 的 shell 工具执行 `curl --max-time 2` 返回 7 / 无法连接；同一服务由宿主独立调用返回 HTTP 200，服务日志仅记录宿主请求。这表明此处 read-only 工具写入和 loopback 访问被阻断；由于该模式不能执行 Task 所需写入，也未验证任意网络、进程和宿主 API 边界，不能据此启用 Executor。临时目录和服务随后清理。

随后用仅含固定 `dhr_probe` 工具的本地合成 stdio MCP server 验证受控桥接入口：`--ignore-user-config --disable shell_tool --sandbox read-only` 加显式 `mcp_servers.dhr_probe` CLI 配置。未给工具配置授权时，thread `01a0b021-6481-7b61-b76b-e6e4517db72d` 的调用被 `approval policy is never` 拒绝；显式设置该工具 `approval_mode="approve"` 后，thread `01a0b023-3e47-7853-9917-b90ca6c03fa0` 收到固定 `DHR_MCP_OK`。再让同一可信 MCP server 只写隔离临时文件，thread `01a0b024-276e-7811-905c-688e5b2e97f2` 返回 `DHR_MCP_WRITE_OK`，独立读取确认文件实际写入。由此可见 MCP server 的写入**不受 Codex 原生 read-only 工具沙箱阻止**，它只能作为另行实现精确 scope 校验、隔离、审计与静止证明的可信桥接候选，绝不能把这次合成调用视为授权完成。配置键见 [Codex 官方参考](https://developers.openai.com/codex/config-reference)。合成 server 和临时文件随后删除。

另一次 `--disable shell_tool` 合成会话仍出现原生 patch 工具，写入被 read-only 拒绝；该开关不能单独证明宿主只暴露 MCP 工具。

代码侧新增 `CodexEventDecoder`：对单次新 thread 的 JSONL 顺序、最终 JSON 文本和 `TaskExecutionRequest` 身份进行校验，遇到重复、失败、畸形或尾随事件后保持拒绝状态；原始事件仍须由后续控制器逐块落盘。这只是结果解码组件，尚未启动或控制真实 Task 进程，也未提供 `authorizationEnforced` 证据。

项目内的 `dhr_propose_text` stdio MCP server 现只校验仓库相对路径与 UTF-8 大小，返回内容 SHA-256 标记，不读写工作树。隔离空目录中以 `--ignore-user-config --disable shell_tool --sandbox read-only` 及显式工具 `approval_mode="approve"` 调用真实 Codex 0.154.0，thread `01a0b038-2652-7b22-b53d-c8d197dfb1a8` 的 `mcp_tool_call` 对 `src/synthetic.txt` / `HELLO` 返回 `PROPOSED 3733cd97…83e4d5`，独立 `find` 确认工作区未创建文件。事件解码器已增加对提议调用的开始/完成配对、工具身份和回执哈希校验，专项 3/3 通过；跨包合成事件 → Core 内存暂存测试 1/1 通过，现同时核对结果 `changedFiles` 与暂存路径一致。两者尚未接入进程控制器、持久证据或安全文件应用器，不能标记为可运行 Executor。临时目录已删除。

`decodeCodexExecution` 进一步把任意分块的 UTF-8 JSONL 原始字节先交给 Core 日志回调，再按行解码、绑定请求并返回提议；日志失败、非法 UTF-8 或超过边界时不交付结果。分块与日志失败专项 2/2 通过，`pnpm build` 和 `pnpm harness:quick` 通过。该入口尚未集成生产进程控制器及取消后静止证明；此项不是新的宿主能力通过记录。

随后在独立空 `/tmp/dhr-codex-decode-smoke-*` 中，用一次性脚本启动真实 Codex 0.154.0：`--ephemeral --ignore-user-config --ignore-rules --disable shell_tool --sandbox read-only --skip-git-repo-check --json`，只装载项目纯提议 MCP 工具，并明确允许该工具。模型调用 `dhr_propose_text(src/a.ts, HELLO)` 后返回与合成 `TaskExecutionRequest` 绑定的 `blocked` 结构化 JSON。脚本把实际 stdout 按 4096 字节切块送入 `decodeCodexExecution`，校验原始日志回调字节与 stdout 完全一致、提议和 `changedFiles` 均为 `src/a.ts`，独立检查目标文件不存在；thread ID `01a0b383-f12b-7cd2-b8fd-d549a5d2c386`。临时工作区和脚本已删除。这验证真实宿主输出能通过当前解码入口，但日志回调在本次脚本中仅保存于内存；生产进程控制、Run 证据持久化、工具目录封闭、取消静止与受控应用仍未通过。

共享 Core 随后新增 `persistWorkerProposals` / `loadWorkerProposals`：在真实临时 Git 仓和权威 `run.json` 上，当前 RUNNING/EXECUTE 的提议被写为不可变 Run 私有证据，回读重验请求、前快照、文件内容和结果声明；重复同字节写入可恢复，异字节、越界、错身份、旧 revision 和工作树漂移被拒。专项 2/2、`pnpm build` 与 `pnpm harness:quick` 通过。此项只验证 Core 的持久候选记录；Codex 真实会话尚未连接该入口，且缺少生产进程控制与受控应用，不能据此启用 Executor。

Codex Adapter 又新增进程传输组件 `runCodexProcess`：以显式二进制、参数、工作目录和环境启动单个进程，关闭 stdin，先将 stdout JSONL 和 stderr 原始字节交给 Core 提供的日志回调，再交付已绑定请求的结构化结果；非零退出、日志持久化失败和取消均拒绝交付。事件解码器也拒绝原生命令、文件改动、网页搜索与未知事件类型，不能以忽略事件掩盖未授权工具。取消只杀死直接子进程，无法证明逃逸后代静止，因此明确返回 `QUIESCENCE_UNKNOWN`，不得据此启用自动 Executor。`pnpm build`、`pnpm harness:quick` 和 Codex 解码 / 传输定向测试 9/9 通过；该子进程测试需在能实际捕获子进程 stdout 的环境执行，当前受限命令沙箱会抑制该输出。
