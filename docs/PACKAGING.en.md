# Shared packaging pipeline

[English](PACKAGING.en.md) | [简体中文](PACKAGING.md)

K10-B supplies the shared inputs, stage gates, and static validation used by platform Packagers, verified with an explicitly registered Fake Packager. K5-P / K6-P / K7 / K8 / K9 / K10-G connect real Packagers for Codex, DSH, Cursor, OpenCode, Antigravity, and Portable. Default `dhr` lists six platform IDs without treating descriptors as executable capabilities. Commands without an explicitly injected trusted BuildPipeline still return `CAPABILITY_MISSING` and do not load executable configuration from projects.

## Sources and dependency graph

```text
protocol-lock.json + pinned, clean upstream checkout
Repository Skills + compiled Runtime / Adapter bundles
build/manifests/metadata.json + actual distribution-notice references
                   ↓
        PluginBuildInput (versions, commits, SHA-256, explicit UTC time)
                   ↓
pnpm build → trusted BuildPipeline.generate → .generated/<platform>/plugin/
                                            + generated.json
                   ↓
           BuildPipeline.validate → validation.json
                   ↓
           BuildPipeline.pack → dist/<platform>/...
                                + dist/manifest.json
                                + dist/build-evidence.json
```

`pnpm build` only compiles the TypeScript workspace and standalone CLI bundle; it does not call `generate`. `generate` does not compile, `validate` does not generate, and `pack` does not generate or validate. Callers compile first, assemble `PlatformRegistry`, `PluginBuildInput`, `StaticSpec`, and `BuildPipeline` through trusted code, and pass the same Registry to the CLI. CLI `run` and packaging commands read that same Registry. Only entries with real RuntimeAdapters execute; only entries with real PluginPackagers package artifacts. Project data and environment variables cannot inject code. Different Registry objects or project roots are rejected.

`PluginBuildInput` is the only version and source input: platform, release/Adapter/Core versions, Skill and bundle digests, protocol lock, metadata, and explicit UTC time. Source checkouts must match their declared Git HEAD. The upstream protocol checkout must be clean, and every locked file's SHA-256 must match; repository Skills, bundles, and distribution notices are also verified against actual bytes. Every stage rechecks sources and the generated directory after Packager callbacks; drift cannot produce a successful record. Shared metadata comes only from [metadata.json](../build/manifests/metadata.json); platforms inject only fields required by their formats. Constrained Skill transformation accepts only `{{DHR_PATH}}`, `{{DHR_COMMAND}}`, and `{{DHR_INVOKE}}`, without rewriting workflows.

The project uses the [MIT license](../LICENSE). The packaged [distribution notice](../build/manifests/DISTRIBUTION_NOTICE.md) includes the complete project license and [third-party notices](../THIRD_PARTY_NOTICES.md). `metadata.licenseRefs` must reference real files with matching digests. When shared metadata permits external distribution, it also checks that the project license and third-party texts actually appear in the packaged notice. Uncommitted local inputs may be verified and marked `localUnversioned` in `dist/build-evidence.json`. GitHub Release gates additionally require committed sources without drift, actual sizes and SHA-256 digests for all nine artifacts, and agreement with versions and the changelog.

## Static validation and archives

Each platform provides an explicit nonempty `StaticSpec`: required files, allowed files, closed JSON-manifest schemas, Skill files, version fields, and file-reference fields. Shared validation covers all ten checks from design §29: manifest structure, required files, canonical relative paths, Skill frontmatter, duplicate Skills, unsupported fields, package content, versions, unfinished markers, and absolute local paths. Nested manifest objects must also be closed; unknown fields fail. References must exactly identify packaged files. Shared JSON validation currently accepts only constrained scalar `name` / `description` Skill frontmatter. Corresponding Packager `validate` implementations must handle platform-specific non-JSON formats; shared checks do not establish host-format validity.

Text scanning covers decodable package content, including JS bundles. `https:` URLs and recognized `$(git …)` expressions may remain; concrete absolute local paths and TODO/TBD/FIXME markers are rejected. This is conservative lint: it does not interpret script semantics or prove plugin installation or Agent execution. Platform reports are combined with shared checks, and any error makes `valid=false`. `pack` accepts only a directory whose current inputs, generated inventory, actual bytes, and validation record agree. After packaging, it rechecks the source directory and each artifact's size and digest. A per-platform `.stage.lock` prevents stages from overwriting one another; the root `.manifest.lock` serializes cross-platform manifest updates. Crash-leftover locks require verification and manual handling rather than automatic removal. `dist/manifest.json` records artifact facts rather than runtime capability.

`createTarGzip` and `createZip` accept only canonical in-memory relative paths and ordinary-file bytes, sorted by UTF-8 path. They reject case aliases, path escapes, and format-boundary overflows. TAR uses USTAR, mode 0644, and uid/gid 0; gzip mtime is 0. ZIP uses fixed Unix mode 0100644, no extra fields, and UTC time rounded down to DOS two-second precision. Archive times come from the input's explicit `buildTimestamp`, never the current clock. ZIP64 is unsupported; exceeding classic-format limits fails.

Golden snapshots are in [tests/packaging/golden](../tests/packaging/golden/). Normal comparisons are read-only and fail on drift. Only an explicit maintainer call to `compareGolden(path, snapshot, { update: true })` writes new goldens, after which inputs and SHA-256 require review. Subsequent platform Packagers should add format fixtures, goldens, and real installation smoke evidence. The Fake Packager alone does not prove availability of all six platforms.

Codex's trusted entry is `createCodexBuildPipeline(root, protocolCheckout)`. The caller supplies the pinned clean upstream protocol checkout; inputs are built from this repository's Git HEAD, real Skill / CLI / Adapter bundles, shared metadata, and commit time. `generate` writes Marketplace source layout under `.generated/codex/plugin/`; `validate` checks closed manifests, source versions, three Skills, relative references, and bundle digests; `pack` produces one `dist/codex/dev-harness-codex-v<version>.zip`. After extracting the ZIP, pass the `marketplace/` path to `codex plugin marketplace add`. Packaged `runtime/source.json` pins protocol sources, Worker Skill, CLI, and Adapter bytes. For run / resume / reconcile only, `scripts/dhr.mjs` assembles Codex RuntimeServices from these bytes; every actual Task still requires a real host capability probe. Linux hosts require usable Codex authentication, Node, Git, and bubblewrap; `DHR_BWRAP` can select a trusted local provider. See the [execution contract](CONTRACTS.en.md#frozen-declaration-for-automatically-executed-tasks) for Task declarations. `--commit-each` currently supports only the default Chinese Conventional Commits template explicitly adopted in the project Workflow. Actual packaged dispatch, original Worker, autonomous Task, Core independent acceptance, per-task commits, and cross-process recovery have passed WSL2 Codex checks. Native Windows passed Marketplace installation, Skill discovery, and read-only version self-check using the same ZIP, but cannot run an Executor requiring Linux isolation. See [K5](verification/K5.md).

Compiled CLI bundles contain placeholder-word regular expressions from validator source and dependency comments, which ordinary text lint would misclassify as package content. Codex StaticSpec skips lexical text lint only for two source-locked bundles whose SHA-256 exactly matches `PluginBuildInput`; any byte drift reports `BUNDLE_DIGEST_MISMATCH`. Manifests, Skills, READMEs, scripts, and notices still undergo shared static scanning. This exception covers only locked code bytes, not arbitrary generated files.

DSH's entry is `createDshBuildPipeline(root, protocolCheckout)`. It generates `package.json`, `cordis.patch.yml`, compiled Cordis plugin / CLI, three Skills, locked `source.json`, and the local notice, then produces a versioned tgz under `dist/dsh/`. The [DSH Packager](../build/targets/dsh.ts) defines the exact filename, also recorded in `dist/manifest.json`. `package.json.dsh.bundle.patch` points to YAML relative to the package root; peers precisely record Cordis 4.0.2 and dsh-commands rc.2 actually resolved by the local rc.1 launcher. The plugin exposes readable `/dhr-status` and controlled tools in Worker scope. Its packaged CLI enables an Executor only after a real host capability probe. See [K6-P](verification/K6-P.md) for installation, CommandRuntime invocation, and removal, and [K6](verification/K6.md) for original Worker and three-task execution evidence. DSH's two locked JS bundles use the same SHA-256-bound exception; other text remains subject to shared lint.

Cursor's entry is `createCursorBuildPipeline(root, protocolCheckout)`. It generates native `.cursor-plugin/plugin.json`, three shared Skills, one requestable rule, one read-only status command, and the packaged CLI, producing `dist/cursor/dev-harness-cursor-v<version>.zip`. The ZIP has a top-level `dev-harness/` directory; place it in Cursor's documented local-plugin directory and reload. Offline content checks, packaged CLI checks, and the `status` Skill's read-only version self-check in an authenticated Cursor Agent CLI isolated `--plugin-dir` session passed. Editor Customize UI, native slash-command registration, and an automatic Executor remain unverified; see [K7 verification](verification/K7.md).

OpenCode's entry is `createOpenCodeBuildPipeline(root, protocolCheckout)`, generating an npm tgz and project-local ZIP from the same locked inputs. The tgz contains `package.json`, JS plugin exports, compiled bundles, fixed `scripts/dhr.mjs`, and three Skills. The ZIP uses `.opencode/plugins/` and `.opencode/skills/`, plus `.opencode/scripts/dhr.mjs` and a version manifest. Skills, scripts, bundles, and the manifest from the npm package must separately be copied into their corresponding project `.opencode/` directories; OpenCode does not promise automatic Skill discovery from npm plugins. Do not install both plugin variants together. The plugin's default export satisfies both OpenCode 1.18.31 `server()` and 2.0.15 `setup()`. Both hosts loaded the plugin and discovered three Skills in isolated projects. The unpublished tgz was automatically installed by package name through a temporary localhost registry; both host versions obtained the current generated package, and 2.0.15 reported it active. A model session loaded the shared Skill through host `skill(status)`. See [K8 verification](verification/K8.md).

Antigravity's entry is `createAntigravityBuildPipeline(root, protocolCheckout)`, generating three ZIP variants from the same Skills: Agent Plugin, project `.agents/skills/`, and standalone global Skills. Each variant includes the same project license and third-party notices at its installation location. Plugin `plugin.json` uses Agent Plugins 1.0.0. Local `agy plugin validate/install/list/uninstall` confirmed processing of all three Skills and global installation, discovery, and removal. For project scope, extract the Plugin ZIP into `<project>/.agents/plugins/dev-harness/`; static validation in an isolated project passed, while session activation remains unverified. Model-session Skill invocation was waived by the user and remains untested. Standalone Skill installation is also unverified; the installation chain must not be described as Executor capability. See [K9 verification](verification/K9.md).

Portable's entry is `createAgentPluginBuildPipeline(root, protocolCheckout)`. It generates only root `plugin.json`, three shared Skills, README, and a distribution notice, producing `dist/agent-plugin/dev-harness-agent-plugin-v<version>.zip`. This artifact has no independent Executor; `dhr run --adapter agent-plugin` returns `CAPABILITY_MISSING` without a trusted Executor. Build-input contracts still require an `adapterBundle` source, so this packaging-only target binds its own compiled Packager file as a source digest; it is not used as execution capability. See [K10-G verification](verification/K10-G.md).

## Verification entry points

[HARNESS](../HARNESS.en.md) owns project build and test commands. The trusted six-platform entry is `createRepositoryBuildPipeline(root, protocolCheckout)`. Repository scripts `pnpm generate`, `pnpm validate:plugins`, `pnpm run pack`, and `pnpm dhr release --dry-run` all require explicit `--protocol-checkout`; see [release documentation](RELEASE.en.md). `pnpm pack` is pnpm's own command and does not replace this project's pack script. See the [verification record](verification/K10-B.md) for reproducible K10-B checks. The release workflow reruns full `pnpm verify` for tags.
